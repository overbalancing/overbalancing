Development and review

Linux setup and launch

Install Rust with rustup and these Debian/Ubuntu system packages. The current rendering-only feature set does not require ALSA development libraries.

sudo apt-get update
sudo apt-get install build-essential pkg-config libudev-dev libx11-dev libxi-dev libxkbcommon-dev libwayland-dev libvulkan1 mesa-vulkan-drivers
rustup toolchain install 1.99.0 --profile minimal --component rustfmt --component clippy
cargo run --locked -p overpalancing-app --bin overpalancing

Run Cargo commands from the repository root in a graphical Linux session with Vulkan support. The pinned development toolchain is stable Rust 1.99.0; the minimum supported Rust version (MSRV) is stable 1.97.1. CI checks that MSRV on a nightly schedule.

First-view controls

Controls are to be documented when the first-view interaction is implemented and reviewed. Keyboard, pointer and touch behavior must match the feature's acceptance scenarios; no unverified control mapping is promised here.

Responsibilities

The lead coordinates work and questions. The architect investigates crates, evaluates alternatives, maintenance activity, reputation and bus factor, and records recommendations. Marc-Hendric Lühr confirms technology choices. Implementers deliver bounded features; the UX engineer owns interaction, readability and accessibility. Implementers escalate only urgent blockers or decisions that require the lead.

Changes and decisions

Specs, ADRs and project documentation are authored in HTML. ADRs live in the repository-root adr/ directory. Only the owner may merge a change that transitions an ADR to approved. The lead may merge documentation, CI and chore pull requests within the owner's authorization; feature and story merges require owner review.

Each feature or story pull request delivers a complete feature. Clean the branch before opening the pull request so it contains one to six coherent commits. Keep unrelated changes out of the branch and preserve already published history unless a coordinated rewrite is authorized.

Specification lifecycle

  1. Locate a matching capability in the specification index. Assign each incoming idea to an existing capability or propose a new one; preserve unresolved questions explicitly.
  2. Create specs/changes/<change-id>/ with HTML proposal, design, tasks and scenarios. Link affected current capabilities and ADRs. This workflow borrows OpenSpec concepts; it does not claim OpenSpec CLI compatibility.
  3. Record observable acceptance criteria and actual validation evidence. Leave unverified tasks pending. Decisions needing the owner receive a stable question identifier.
  4. After implementation and acceptance, integrate the accepted behavior into specs/current/, record the merge and verification evidence, and move the change to specs/archive/. Preserve links or update every incoming reference.

Validation

Run formatting, Clippy, nextest and documentation checks for the affected code. CI also covers security audit, dependency policy, scheduled MSRV checks and supported target builds. Use stable Rust for ordinary development; the MSRV job runs on a nightly schedule, not on the nightly compiler. Build success and runtime verification are recorded separately.

See verification evidence for recorded checks and remaining runtime validation.

Assets

The primitive first view needs no external assets. If assets become necessary, request the exact component, intended use, pixel dimensions, format, transparency and variants before integrating them.

CI operations

Self-hosted Renovate follows the workflow reference. Configure a least-privilege RENOVATE_TOKEN repository secret before its scheduled run; do not reuse broad personal credentials. The token needs access to this repository and permission to create dependency branches and pull requests. No secret belongs in source or chat. Dependency PRs are reviewed before merge.

Pages publishes the preserved docs/, adr/ and specs/ trees plus Rustdoc under api/. Configure GitHub Pages to use GitHub Actions. PR builds validate links; deployment runs only from main. CI artifacts provide desktop archives, an Android debug APK, and an ad-hoc signed iOS simulator app archive. Simulator signing is not App Store distribution signing.

CODEOWNERS and the PR check assist review. They cannot identify whether an API call using the owner's account was made by the owner or an agent; the lead must never merge ADR approval transitions. Configure branch rules with care: GitHub does not allow an author to approve their own PR.
